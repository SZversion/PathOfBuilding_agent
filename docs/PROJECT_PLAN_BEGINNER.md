# PoB Agent MVP 기획서 — PoE·PoB 입문자용

> 문서 목적: 게임과 도구에 익숙하지 않은 팀원·협력자도 제품의 필요성과 MVP 범위를 이해할 수 있도록 설명한 내부 기준서  
> 상세 기술 기준: [PROJECT_PLAN.md](PROJECT_PLAN.md), [AGENT.md](../AGENT.md), [PRD_SDD.md](../PRD_SDD.md) 참조

## 1. 한눈에 보는 프로젝트

**PoB Agent**는 액션 RPG 게임인 *Path of Exile 1*의 캐릭터 빌드를 분석해 주는 AI 기능이다. 사용자는 복잡한 수식이나 도구 화면을 직접 해석하지 않아도, 자연어로 질문하여 자신의 캐릭터가 왜 강하거나 약한지 확인하고 특정 장비·스킬·패시브 변경의 효과를 비교할 수 있다.

이 제품은 기존 계산 도구인 **Path of Building Community(PoB)**에 붙는 확장 기능이다. PoB의 계산을 새로 만들거나 교체하지 않는다. 대신 PoB가 이미 계산한 정확한 결과를 읽고, 사람이 이해하기 쉽게 설명하며, 사용자가 요청한 안전한 변경만 PoB 화면에 반영한다.

## 2. 먼저 알아둘 용어

### Path of Exile 1 (PoE)

Path of Exile 1은 장비, 스킬, 패시브 능력, 버프, 적의 상태 등을 조합해 캐릭터를 만드는 게임이다. 4개월 주기로 시즌이 진행되어 약 16만명의 유저가 즐기고 있다. 선택지가 많아 작은 변경도 공격력·생존력·스킬 동작 방식에 큰 영향을 줄 수 있다.

### 빌드(Build)

빌드는 한 캐릭터를 구성하는 전체 설계도다. 사용하는 스킬, 장비, 패시브 트리, 보조 스킬, 각종 조건과 설정을 모두 포함한다.

### Path of Building Community (PoB)

PoB는 빌드 설계도를 열어 보고, 캐릭터의 피해량·생명력·방어력·스킬 동작을 계산하는 데스크톱 도구다. 계산 정확도가 높지만, 결과가 만들어진 이유를 이해하거나 복잡한 변경을 비교하려면 상당한 경험이 필요하다.

### PoB Agent

PoB Agent는 PoB 안에 추가되는 별도 AI 창이다. 사용자는 다음처럼 질문한다.

- “내 주력 스킬의 피해량이 왜 이 수치인가?”
- “이 무기로 바꾸면 피해량이 얼마나 달라지나?”
- “이 보조 스킬을 바꾸면 무엇을 잃고 얻나?”

Agent는 PoB의 최신 계산 결과를 바탕으로 답하고, 근거와 한계를 함께 보여 준다.

## 3. 해결하려는 사용자 문제

PoE는 빌드 조합의 자유도가 높은 만큼, 사용자가 현재 상태를 이해하기 어렵다. PoB는 이를 계산해 주지만, “숫자를 보여 주는 도구”에 가깝기 때문에 해석과 의사결정의 부담은 여전히 사용자에게 남는다.

### 3.1 주요 페인포인트

| 사용자 문제 | 실제로 겪는 상황 | PoB Agent가 제공할 해결 방식 |
| --- | --- | --- |
| 숫자의 이유를 알기 어렵다 | 피해량은 보이지만 어떤 장비·스킬·조건이 영향을 줬는지 파악하기 어렵다. | 최종값뿐 아니라 영향 요인과 계산 경로를 설명한다. |
| 변경의 결과를 예측하기 어렵다 | 장비나 보조 젬 하나를 바꾸기 전에 무엇이 달라질지 확신하기 어렵다. | 변경 전후 수치와 메커니즘 차이를 비교한다. |
| PoB 화면 조작이 복잡하다 | 아이템, 젬, 패시브, 설정이 여러 화면에 흩어져 있어 초보자가 실수하기 쉽다. | 자연어 요청을 검증된 PoB 변경으로 변환한다. |
| 현재 어떤 조건이 적용되는지 놓치기 쉽다 | 선택된 스킬 세트, 메인 스킬, 버프, 적 상태에 따라 계산이 달라진다. | 현재 적용 상태를 기준으로 답하고, 핵심 조건을 함께 알려 준다. |
| 온라인 정보의 신뢰도를 판단하기 어렵다 | 공략·위키·영상의 설명이 내 빌드나 현재 버전과 다를 수 있다. | PoB 계산값, 외부 참고, 추론을 분리해 표시한다. |
| 수정 중 빌드를 망가뜨릴까 걱정된다 | 실험하다가 기존 설정을 잃거나 파일을 덮어쓸 수 있다. | 화면의 메모리 상태만 바꾸고 자동 저장하지 않는다. |

### 3.2 제품이 약속하는 경험

사용자는 “복잡한 계산을 대신해 주는 AI”가 아니라, **PoB가 계산한 결과를 믿을 수 있게 읽어 주고 안전하게 실험하도록 돕는 조력자**를 얻는다. 자동차에 비유하면 PoB는 실제 측정 장비와 정비 시스템이고, PoB Agent는 측정 결과를 설명하고 사용자의 요청에 따라 검증된 조정만 돕는 안내자다.

## 4. 대표 유즈케이스

### 유즈케이스 1 — 내 피해량의 원인 이해하기

**상황:** 사용자는 주력 스킬의 DPS가 기대보다 낮은 이유를 모른다.  
**질문:** “내 Arc 피해량이 왜 이 정도야?”

1. Agent가 현재 선택된 주력 스킬, 스킬 세트, 버프, Config를 확인한다.
2. PoB가 계산한 최종 피해량과 중간 계산 근거를 읽는다.
3. 장비·젬·패시브·조건 중 큰 영향을 준 요소를 정리한다.
4. 사용자에게 결론, 수치, 영향 요인, 근거, 불확실성을 차례로 설명한다.

**사용자 결과:** 사용자는 단순히 “피해량이 낮다”가 아니라, 어떤 조건이나 구성 요소를 확인해야 하는지 이해한다.

### 유즈케이스 2 — 새 장비로 바꿨을 때 비교하기

**상황:** 사용자는 거래에서 찾은 무기로 교체할지 고민한다.  
**질문:** “이 무기로 바꾸면 DPS가 얼마나 오르지?”

1. Agent가 아이템 텍스트 또는 사용자가 지정한 대상 아이템을 확인한다.
2. 현재 상태와 아이템 교체 후 상태를 PoB 기준으로 비교한다.
3. 피해량뿐 아니라 생존력, 저항, 스킬 조건 등 주요 변화도 확인한다.
4. 사용자가 명시적으로 요청한 경우에만 검증된 교체를 현재 PoB 화면에 적용한다.

**사용자 결과:** 사용자는 숫자 변화와 그 이유를 함께 보고, 실제 저장 전 화면에서 안전하게 선택을 검토한다.

### 유즈케이스 3 — 보조 젬을 바꿔도 되는지 확인하기

**상황:** 사용자는 보조 젬 하나를 다른 젬으로 교체하려 한다.  
**질문:** “이 보조 젬 대신 다른 젬을 넣으면 더 좋아?”

1. Agent가 현재 스킬 링크, 젬 레벨, 퀄리티, 변형 여부를 확인한다.
2. 두 구성을 비교해 피해량, 공격·시전 속도, 자원 점유, 스킬 동작의 변화를 확인한다.
3. 특정 조건에서만 이득인 경우 그 조건을 명확히 알린다.

**사용자 결과:** 사용자는 한 개의 큰 숫자만 보고 판단하지 않고, 실제 플레이에 필요한 조건과 손해까지 고려할 수 있다.

### 유즈케이스 4 — 빌드 메커니즘을 쉽게 이해하기

**상황:** 사용자는 다른 사람의 PoB 코드를 불러왔지만 빌드의 핵심 구조를 모른다.  
**질문:** “이 빌드는 어떤 방식으로 피해를 내?”

1. Agent가 주력 스킬, 핵심 장비, 주요 패시브와 활성 조건을 파악한다.
2. PoB 결과와 로컬 게임 지식을 함께 사용해 핵심 상호작용을 설명한다.
3. PoB에서 확정된 값과 일반 게임 규칙 설명을 구분해 보여 준다.

**사용자 결과:** 사용자는 복잡한 트리와 장비 목록을 모두 읽지 않고도 빌드의 핵심 원리를 이해한다.

### 유즈케이스 5 — 두 빌드의 차이 비교하기

**상황:** 사용자는 현재 빌드와 다른 PoB 코드를 비교하고 싶다.  
**질문:** “이 두 빌드는 무엇이 다르고, 어느 쪽이 더 튼튼해?”

1. Agent가 각 빌드의 게임·PoB 버전과 비교 가능 여부를 확인한다.
2. 주요 스킬, 피해량, 생존력, 조건, 핵심 장비·패시브의 차이를 정리한다.
3. 버전이 크게 다르거나 근거가 부족하면 비교를 멈추고 이유를 설명한다.

**사용자 결과:** 사용자는 단순한 우열 판단이 아니라 각 빌드의 특징과 선택 조건을 이해한다.

## 5. MVP에서 제공하는 기능

MVP는 사용자가 지정한 내용을 **조회, 설명, 비교, 변경**하는 데 집중한다.

| 기능 | 쉬운 설명 |
| --- | --- |
| 수치 조회·근거 추적 | 피해량·생존력·지속시간 같은 숫자와 원인을 보여 준다. |
| 아이템 교체·비교 | 장비를 바꿨을 때 달라지는 결과를 확인한다. |
| 젬 교체·비교 | 스킬과 보조 젬 조합의 차이를 확인한다. |
| 패시브·주얼 변경·비교 | 트리와 주얼 변경의 효과를 확인한다. |
| 변경 전후 설명 | 숫자 변화의 원인과 게임 플레이상 의미를 설명한다. |
| 빌드 메커니즘 설명 | 현재 빌드가 작동하는 핵심 원리를 알려 준다. |
| 다른 빌드 비교 | 불러온 다른 빌드와 장단점을 비교한다. |

### MVP에서 하지 않는 일

- 사용자의 목표를 추측해 자동으로 장비·젬·패시브를 추천하지 않는다.
- PoB와 별도로 계산기를 만들어 새로운 정답을 내지 않는다.
- 사용자의 파일을 자동으로 저장하거나 새 파일을 자동 생성하지 않는다.
- PoE 2 또는 메이저 버전이 다른 빌드의 계산을 지원하지 않는다.

## 6. 사용자가 보게 될 흐름

```text
사용자 질문
  ↓
PoB Agent가 현재 PoB 상태를 확인
  ↓
PoB의 계산 결과와 근거를 읽음
  ↓
필요하면 안전한 범위에서 비교·변경 수행
  ↓
결론 + 수치 + 이유 + 출처 + 주의 사항을 답변
```

사용자는 기존 PoB를 평소처럼 계속 사용한다. Agent는 PoB 화면을 대체하지 않고, 별도 창에서 도움을 제공한다.

## 7. 결과를 믿을 수 있는 이유

### 7.1 PoB가 계산의 기준이다

Agent가 게임 수치를 추측하거나 독자적으로 계산하지 않는다. PoB가 현재 빌드에 대해 계산한 결과를 읽고 설명한다. 그래서 Agent의 역할은 “정답을 새로 만드는 것”이 아니라 “이미 계산된 정답을 근거와 함께 전달하는 것”이다.

### 7.2 현재 화면이 항상 우선이다

사용자가 PoB에서 직접 바꾼 내용은 Agent가 이전에 기억한 내용보다 우선한다. Agent가 변경을 적용하기 직전에 상태가 달라졌다면, 이전 변경 요청은 폐기하고 최신 화면을 다시 기준으로 삼는다.

### 7.3 근거를 함께 제공한다

답변에는 가능한 범위에서 다음 정보가 포함된다.

- 최종 수치와 중간 계산값
- 수치에 영향을 준 장비, 젬, 패시브, 버프, 조건
- PoB 내부 계산 근거
- 로컬 게임 지식 또는 외부 참고 출처
- 게임·PoB 버전 및 결과의 확실성

근거가 충분하지 않으면 Agent는 그럴듯하게 추측하지 않고, 필요한 정보를 묻거나 답변할 수 없음을 알린다.

## 8. 안전한 변경과 저장 방식

사용자가 특정 변경을 요청하면 Agent는 먼저 대상과 현재 상태를 검증한다. 그 뒤 변경을 적용하고 PoB가 재계산한 결과를 확인한다.

중요한 원칙은 다음과 같다.

- 사용자 요청 없이 빌드를 바꾸지 않는다.
- 변경은 현재 열려 있는 PoB 화면의 메모리 상태에만 적용한다.
- Agent는 자동 저장, 자동 백업, 자동 `Save As`를 하지 않는다.
- 최종 저장은 사용자가 기존 PoB의 `Save` 또는 `Save As`로 결정한다.
- 변경 중 오류가 나면 이전 상태로 되돌릴 수 있도록 처리한다.

즉, 사용자는 새 구성을 시험해 본 뒤 마음에 들 때만 기존 PoB 방식으로 저장할 수 있다.

## 9. 시스템이 동작하는 방식

제품은 역할이 분명한 세 층으로 구성된다.

```text
PoB 본체
  └─ 실제 빌드 정보와 계산 결과를 보유

로컬 PoB Bridge
  └─ PoB 상태를 안전하게 읽고, 검증된 변경·검색을 수행

외부 AI 서버
  └─ 사용자의 문장을 이해하고, 실행 계획과 쉬운 설명을 생성
```

### PoB 본체

빌드 정보와 실제 계산을 보유하는 원본 도구다. 저장과 불러오기 역시 PoB가 계속 담당한다.

### 로컬 PoB Bridge

사용자의 PC에서 PoB와 AI 사이를 연결하는 안전 장치다. 어떤 작업을 할 수 있는지 검사하고, 현재 상태가 바뀌지 않았는지 확인하며, 필요한 결과를 가져온다.

### 외부 AI 서버

사용자 질문을 이해하고 설명을 작성한다. 이 서버는 사용자의 로컬 파일, PoB 메모리, 운영체제 명령을 직접 볼 수 없고 실행할 수도 없다.

## 10. 개인정보와 보안 원칙

- 외부 AI에는 원본 PoB 파일(XML)을 보내지 않고, 필요한 내용만 정리한 상태 정보만 전달한다.
- 외부 AI가 사용자의 PC 파일을 직접 읽거나 명령을 실행할 수 없다.
- 허용된 작업 목록과 형식을 통과한 요청만 실행한다.
- MVP는 사용자 API 키나 로컬 모델 설치를 요구하지 않는다.
- 사용자 API 키가 있다면 모델 입력, 상태 정보, 로그, 캐시에 포함하지 않는다.
- 외부 검색은 신뢰 가능한 제한된 출처에서만 수행하고, 결과는 임시 참고 자료로 표시한다.

## 11. 오류가 나거나 답할 수 없을 때

좋은 답변보다 중요한 것은 잘못된 답변이나 위험한 변경을 하지 않는 것이다. Agent는 아래 상황에서 멈추고 이유를 알려 준다.

- 질문 대상이 여러 개여서 무엇을 뜻하는지 알 수 없는 경우
- 필요한 스킬·장비·조건 정보가 빠진 경우
- 게임 또는 PoB의 메이저 버전이 달라 비교할 수 없는 경우
- PoB나 신뢰 가능한 근거에서 값을 확인할 수 없는 경우
- 사용자가 Agent 처리 중 PoB 화면을 직접 수정한 경우
- 요청이 지원 범위를 벗어났거나 안전하게 수행할 수 없는 경우

## 12. 개발 순서

1. **기반 마련** — 상태 정보 형식, 오류 형식, 버전 정책, 안전 규칙을 고정한다.
2. **읽기·설명 기능** — 현재 빌드의 수치와 근거를 읽고 설명한다.
3. **비교 기능** — 장비, 젬, 패시브, 다른 빌드의 차이를 비교한다.
4. **실시간 변경 기능** — 검증, 되돌리기, 재계산을 갖춘 안전한 화면 변경을 구현한다.
5. **출시 검증** — 실제 빌드 사례, 기존 PoB 회귀, 사용자 흐름, 장애 대응을 확인한다.

## 13. 완료 여부를 판단하는 기준

MVP가 준비되었다고 말하려면 다음을 확인해야 한다.

- 핵심 기능 7종이 실제 시나리오와 자동화 테스트로 검증되었다.
- 표시된 확정 수치가 PoB 결과와 일치한다.
- 모든 중요한 결과에 근거와 한계가 표시된다.
- 사용자의 직접 수정과 저장 방식이 손상되지 않는다.
- 오류 상황에서 빌드를 임의로 바꾸거나 근거 없는 답변을 하지 않는다.
- 대표적인 복잡 빌드 사례에서도 기능이 의도대로 동작한다.

## 14. 팀을 위한 핵심 원칙

1. **PoB의 계산이 정답이다.** Agent는 이를 해석하고 전달한다.
2. **사용자 상태가 우선이다.** Agent의 편의보다 사용자가 직접 바꾼 내용을 보호한다.
3. **근거 없는 확신은 금지한다.** 모르면 묻고, 확인할 수 없으면 명확히 말한다.
4. **안전한 실험을 돕는다.** 저장 권한은 사용자에게 남긴다.
5. **지원 범위를 솔직하게 표시한다.** 모든 게임 메커니즘을 안다고 주장하지 않는다.

이 원칙을 지키면 PoB Agent는 복잡한 빌드 도구의 진입 장벽을 낮추면서도, PoB가 제공하는 계산 신뢰도를 훼손하지 않는 제품이 된다.
